# 잇다 — 역할 분담 및 협업 규칙

## 1. 협업 원칙

- **작업 관리:** 모든 작업은 GitHub Issue로 공유하며, 하나의 Issue는 가능한 한 하나의 명확한 목표를 갖는다.
- **브랜치 관리:** 작업별 브랜치를 생성하고, 최신 `main`을 기준으로 개발한다.
- **코드 반영:** `main`에 직접 Push하지 않고 PR을 통해 반영한다.
- **코드 리뷰:** PR은 다른 팀원의 리뷰와 승인 후 `Squash and Merge`한다. 본인의 PR은 스스로 승인하지 않는다.
- **작업 완료:** 기능 구현뿐 아니라 필요한 테스트와 문서 수정까지 완료하고, 배포 대상인 경우 실제 배포 환경에서도 정상 동작을 확인한다.
- **역할 분담:** 프론트엔드와 백엔드로 역할을 구분하지 않고 기능 단위로 분담한다. 두 사람 모두 Flutter 화면 개발과 Spring Boot 기능 개발에 참여하며, 작업량과 난이도를 고려해 업무를 배분한다.
- **소통:** 작업 범위, API 규격, 연동 순서 및 일정 변경 사항을 미리 공유한다. 작업에 문제가 생기면 함께 해결하거나 범위를 조정한다.
- **기술 의사결정:** 새로운 기술 도입과 주요 설계 변경은 필요성 및 구현 비용을 고려해 협의한다.
- **보안:** 비밀번호, API Key, Token 등 민감한 정보는 GitHub에 Commit하지 않는다.
- **배포:** Hyeon이 CI/CD 및 배포를 주도하고, Songhaney도 배포 과정에 참여한다.

**기본 작업 흐름**

```text
Issue 생성 및 담당자 확인
          ↓
작업 브랜치 생성
          ↓
개발 및 Commit
          ↓
PR 생성 및 테스트 결과 작성
          ↓
상대 팀원 리뷰 및 승인
          ↓
Squash and Merge
          ↓
배포 환경 확인 및 Issue 종료
```

## 2. R&R

### 2.1 역할 분담

프론트엔드와 백엔드로 구분하지 않고 기능 단위로 담당자를 정한다. 각 담당자는 가능한 범위에서 화면 구현, API 연동, 테스트, 문서 작성까지 수행한다.

| 작업 영역 | 담당자 |
| --- | --- |
| 인증·인가 | Songhaney |
| 게시글 등록·수정·삭제 | Songhaney |
| 게시글 목록·상세 조회 | Hyeon |
| 게시글 검색·필터링 | Hyeon |
| 게시글 매칭 | 공동 |
| 게시글 상태·반환 기록 관리 | Hyeon |
| 사용자 정보·게시글 관리 | Songhaney |
| 채팅방·메시지 관리 | Songhaney 주도, Hyeon 협업 |
| 메시지 푸시 알림 | Hyeon 주도, Songhaney 협업 |
| CI·배포 | Hyeon 주도, Songhaney 리뷰 |
| 테스트·문서 작성 | 각 작업 담당자 |
| 공통 기술 의사결정 | 공동 |

### 2.2 역할 분담 원칙

- 작업량과 난이도를 고려해 특정 인원에게 부담이 집중되지 않도록 담당 업무를 분배한다.
- 매칭 기능은 공동으로 설계하고 구현 범위를 협의한다.
- 추가 기능은 MVP 필수 기능을 우선 완료한 뒤 일정을 고려해 구현 여부를 결정한다.
- 메시지 관리와 메시지 푸시 알림은 상호 연동되도록 구현하며, 메시지 저장·전송 흐름과 알림 전송을 담당자 간 협의해 연결한다.

## 3. 프로젝트 구조

### 3.1 전체 디렉터리 구조

```text
ITDA/
├── .github/
│   └── workflows/
│       └── ci.yml                  # GitHub Actions CI
├── frontend/                       # Flutter 모바일 앱
│   ├── lib/                        # 앱 소스 코드
│   ├── test/                       # Flutter 테스트 코드
│   ├── pubspec.yaml                # 패키지 및 의존성 설정
│   └── analysis_options.yaml       # Dart 정적 분석 설정
├── backend/                        # Spring Boot 서버
│   ├── src/
│   │   ├── main/
│   │   │   ├── java/               # 애플리케이션 소스 코드
│   │   │   └── resources/          # 애플리케이션 설정
│   │   └── test/                   # 테스트 코드     
│   └── build.gradle                # Gradle 빌드 설정
├── docs/                           # 프로젝트 문서
├── .env.example                    # 환경 변수 예시
├── docker-compose.yml              # 로컬 개발 환경
└── README.md                       # 프로젝트 소개 및 실행 안내
```

위 구조는 프로젝트의 기본 디렉터리 구성이다. 실제 구현 상황에 따라 필요한 파일과 하위 디렉터리를 추가한다.

### 3.2 Flutter — lib 디렉터리 구성

| 디렉터리 및 파일 | 역할 |
| --- | --- |
| `main.dart` | 앱의 진입점 |
| `app.dart` | 앱의 최상위 위젯 및 전반적인 설정 |
| `core/` | API 통신, 라우팅, 테마, 공통 상수, 오류 처리 |
| `shared/` | 여러 기능에서 재사용하는 UI 컴포넌트 |
| `features/` | 기능별 화면, 데이터 처리 및 관련 로직 |

`features/`는 다음과 같이 구성한다.

```text
features/
├── auth/          # 인증 관련 화면
├── home/          # 홈 화면
├── posts/         # 게시글 관리 및 매칭 화면
├── search/        # 게시글 검색·필터링 화면
├── chat/          # 채팅 관리 화면
├── returns/       # 반환 상태 관리 화면
└── my_page/       # 마이페이지 화면
```

각 기능 디렉터리의 하위 구조는 실제 구현에 필요한 경우에만 추가한다.

### 3.3 Spring Boot — 패키지 구성

```text
com.itda/
├── global/        # 공통 설정, 보안, 예외 및 응답 처리
├── auth/          # 카카오 로그인 및 인증
├── user/          # 사용자 정보 관리
├── post/          # 게시글 관리
├── search/        # 게시글 검색·필터링
├── matching/      # 게시글 매칭
├── chat/          # 채팅방 및 메시지 관리
└── returnrecord/  # 반환 상태 관리
```

- 기능별 패키지에는 필요한 경우 Controller, Service, Repository, Entity, DTO 등을 구성한다.
- 공통 설정 및 예외 처리 등 여러 기능에서 사용하는 코드는 `global/`에서 관리한다.
- 실제 클래스와 세부 하위 패키지는 구현 시 필요한 범위에서 추가한다.

### 3.4 프론트엔드와 백엔드의 책임

- **Flutter:** 화면 구성, 사용자 입력 처리, API 연동 및 서버 응답 표시

## 4. Issue 규칙

### 4.1 제목

| 유형 | 예시 |
| --- | --- |
| 기능 개발 | `[Feature] 분실물 게시글 등록` |
| 버그 수정 | `[Fix] 로그인 오류 수정` |
| 리팩터링 | `[Refactor] 매칭 로직 개선` |
| 테스트 | `[Test] 게시글 등록 테스트 작성` |
| 문서 수정 | `[Docs] API 명세 작성` |
| 환경 설정 | `[Chore] Flutter 개발 환경 설정` |

### 4.2 내용

```markdown
## 📝 작업 내용
작업의 목적을 작성한다.

- 구현하거나 수정할 내용

## ✅ 완료 조건
- [ ] 요구한 기능이 동작한다.
- [ ] 필요한 테스트를 완료했다.
```

- 작업 범위가 크면 하위 작업으로 나눈다.
- 작업 범위가 변경되면 Issue를 수정하거나 팀원에게 공유한다.
- 작업 완료 후 관련 PR을 연결하고 Issue를 종료한다.

## 5. Branch 규칙

### 5.1 브랜치 구성

| 브랜치 | 용도 |
| --- | --- |
| `main` | 통합된 코드 및 배포 기준 |
| `feature/*` | 기능 개발 |
| `fix/*` | 버그 수정 |
| `refactor/*` | 코드 구조 개선 |
| `test/*` | 테스트 추가·수정 |
| `docs/*` | 문서 작업 |
| `chore/*` | 환경 설정 및 기타 작업 |

### 5.2 브랜치 이름

Issue 번호와 작업 내용을 영문 소문자 및 하이픈으로 작성한다.

```text
feature/12-lost-post-create
fix/21-login-error
refactor/24-match-service
test/25-post-create-test
docs/30-api-spec
chore/31-flutter-setup
```

하나의 브랜치에서는 하나의 Issue를 중심으로 작업한다.

## 6. Commit 규칙

`type: 작업 내용` 형식을 사용한다.

| Type | 용도 |
| --- | --- |
| `feat` | 새로운 기능 |
| `fix` | 버그 수정 |
| `refactor` | 기능 변경 없는 코드 구조 개선 |
| `test` | 테스트 추가·수정 |
| `docs` | 문서 수정 |
| `chore` | 설정 및 기타 작업 |

예시: `feat: 분실물 게시글 등록 구현`

## 7. PR 규칙

### 7.1 제목

작업 유형과 내용을 작성한다.

예시: `[Feature] 분실물 게시글 등록`

### 7.2 내용

```markdown
## 관련 Issue
## 🔗 관련 Issue
- Closes #<!-- 이슈 번호 -->

## ✏️ 변경 내용
- 변경 사항 요약

## 🧪 테스트
- [ ] 정상 동작 확인
- [ ] 관련 테스트 실행
- [ ] 미확인 항목 및 사유 작성

## ⚠️ 변경 영향
- [ ] API 또는 DB 변경 여부 확인
- [ ] 관련 문서 수정 여부 확인
- [ ] 다른 기능에 미치는 영향 확인

## 🔖 리뷰 참고 사항
- 확인이 필요한 부분
```

해당하지 않는 항목은 생략할 수 있으며, 테스트하지 못한 항목은 사유를 작성한다.

### 7.3 리뷰 및 Merge

- 리뷰어는 코드의 목적, 오류 가능성, 테스트 여부를 확인한다.
- 수정 의견은 반영하거나 이유를 설명하고 협의한다.
- 승인 후 작업 담당자가 `Squash and Merge`한다.
- Merge 후 작업 브랜치를 삭제한다.

---

## 8. 테스트 및 완료 기준

PR 생성 전 담당자는 다음 항목을 확인한다.

- [ ] 요구한 기능이 정상 동작한다.
- [ ] 주요 예외 상황과 기존 기능에 미치는 영향을 확인했다.
- [ ] 필요한 테스트를 실행했다.
- [ ] 필요한 문서를 수정했다.

인증·인가, 매칭, 상태 변경 등 핵심 로직은 가능한 범위에서 테스트한다.

---

## 9. 보안 및 환경변수

- 비밀값은 `.env` 또는 배포 플랫폼의 환경변수로 관리하고, 해당 파일은 `.gitignore`에 등록한다.
- 환경변수가 추가되면 변수명과 용도를 `README.md` 또는 `DEPLOYMENT.md`에 기록한다. 실제 비밀값은 기록하지 않는다.

---

## 10. 배포 규칙

- 배포 전 핵심 기능을 점검하고, 배포 후 실제 환경에서 카카오 로그인 및 최초 계정 생성, 게시글 등록·조회, 매칭 후보 확인, 채팅 및 반환 처리 등 주요 흐름을 확인한다.
- 배포 오류는 공유하고, 필요한 경우 수정 Issue를 생성한다.
- 배포 설정과 해결 방법은 `README.md` 또는 `DEPLOYMENT.md`에 기록한다.

**코드 Merge와 배포 환경에서의 정상 동작은 별도로 확인한다.**
